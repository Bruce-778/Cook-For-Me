# 2026-09-27 上线前本地验收记录

这次验收针对当前 `main` 集成版本，重点检查页面可用性、响应式布局、菜谱资料边界、Supabase 同步脚本和 DeepSeek 接口。检查在本地完成，没有部署生产环境，也没有修改远程数据库。

## 已完成的修正

- 移动端页面为底部导航和 iPhone 安全区预留空间；点赞提示不再盖住底部导航。
- 食物盲盒的合并购物清单允许长食材名称换行，数量列不会被挤出卡片。
- AI 接口统一返回 `Cache-Control: no-store`，实际读取请求体并限制 12KB；上游响应限制 100KB；超时、无密钥、上游错误和非法 JSON 都回到站内保守推荐。
- AI 请求不再把哈希后的 IP 作为 `user_id` 发给模型；进程内限流表会清理过期条目并设置上限。
- AI 对明确的过敏、不耐受、肉类禁忌、纯素/素食和清真要求做服务端二次过滤，不能只依赖模型提示词。
- 菜谱参考资料与 B 站搜索入口分开。B 站搜索页只作为用户查找入口，不再冒充做法来源；未核验资料不再填写固定日期。
- Supabase 同步会检查旧明细清理错误，并允许草稿参考资料的核验日期为空。

## 本地验证结果

以下命令均在修改后的工作区通过：

```text
pnpm lint
pnpm typecheck
pnpm validate:content
pnpm validate:ai
pnpm validate:videos
pnpm validate:supabase
pnpm build
```

构建生成 210 个页面。使用 `pnpm exec next start -p 3101` 启动本次构建后，`LOCAL_BASE_URL=http://localhost:3101 pnpm test:local` 通过：6 个主页面、98 个菜谱详情页、98 个烹饪页、98 个详情 API、分页、盲盒忌口和错误边界均返回预期结果。

## AI 接口冒烟

- 使用本地 `.env.local` 的服务端密钥发送了一次真实的普通饮食问题，接口返回 HTTP 200、站内合法菜谱 slug 和 `Cache-Control: no-store`。
- 发送胸痛和呼吸困难描述时，接口直接返回急救分流，不调用模型推荐菜谱。
- 发送超过 12KB 的请求体时，接口返回 HTTP 413。
- 这几项只证明接口链路和边界行为可用，不代表模型回答永远正确，也不把健康建议当成医疗诊断。

## 必须保持透明的内容状态

当前仍是 98 道结构化菜谱，其中 1 道有逐项人工复核记录、97 道仍待实做复核。自动检查能发现字段、引用和逻辑冲突，不能替代在真实锅具上逐道试做。22 道菜有具体 B 站视频直链，另有 76 道保留同名搜索入口；视频能打开也不等于它与本站的用量和火候完全一致。
